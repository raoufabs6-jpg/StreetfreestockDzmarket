# AKMA Business

> **Simple Business Management** — منصة ويب بسيطة وسهلة الاستخدام للتجار وأصحاب المؤسسات الصغيرة والمتوسطة، تجمع في نظام واحد بين الوظائف الأساسية لـ **ERP** و **CRM** — مع طبقة **SaaS متعددة المؤسسات** (Multi-tenant) على **PostgreSQL**.

واجهة عربية بالكامل مع دعم **RTL**، وجاهزة لدعم الفرنسية والإنجليزية لاحقًا.

### عمليات ERP المترابطة (المرحلة 5)

العمليات لا تعمل معزولة — المخزون يتحرك دائمًا عبر **حركات مرتبطة بالمستند**:

- **بيع →** يخصم الكمية ويسجّل حركة `out` مرتبطة (`saleId`) — يُمنع البيع من **منتج موقوف** أو بكمية أكبر من المتوفر **إلا إذا فُعّل `allowOversell`** في الإعدادات.
- **شراء →** يزيد الكمية ويسجّل حركة `in` مرتبطة (`purchaseId`).
- **تعديل بند بيع →** يسوّي المخزون بفروقات حركات تعويضية بنفس تاريخ المستند.
- **حذف بيع →** يعكس **الصافي المحسوب من حركاته المرتبطة فقط**؛ مستند قديم بلا حركات مرتبطة = **بلا أي تعديل مخزون**.
- **حذف شراء معادله →** يخصم ما أضافه؛ يُرفض بـ `400` إن كان الرفض سيعمل الكمية تحت الصفر.
- **تعديل الكمية (`adjust`) →** تعيين **مطلق** للجرد (يقبل الصفر) — يصلح المخزون السالب ويُسجَّل كحركة.
- حركات المخزون اليدوية صارمة دائمًا (لا سلبية مهما كانت الإعدادات).

### نظام الفواتير الاحترافي (المرحلة 6)

الفاتورة **وثيقة مستقلة بعد الإصدار** — تُنشأ من مستند بيع (لقطة تلقائية: العميل، البنود، الأسماء، الخصم، حالة الدفع، رقم البيع) أو يدويًا:

- **لا تلمس المخزون إطلاقًا** — حركات المخزون للمبيعات والمشتريات فقط؛ حذف الفاتورة آمن دائمًا ولا يغيّر المخزون ولا يمسّ البيع المصدر.
- **الإجمالي محسب**: `مجموع البنود − الخصم` (الفواتير اليدوية القديمة بمبلغ واحد محفوظة للتوافق).
- **رقم تلقائي** `INV-XXXX` فريد داخل المؤسسة (التكرار → 409).
- **صفحة `/invoices/[id]`**: ورقة A4 عربية RTL (ترويسة المؤسسة، بيانات العميل، جدول البنود، الإجماليات، التوقيعات) + **طباعة** عبر `@page A4` + **تحميل PDF** (html2canvas-pro + jsPDF) — كل النصوص عبر مفاتيح i18n جاهزة للفرنسية والإنجليزية.
- تعديل بنود البيع لاحقًا **لا يغيّر الفواتير الصادرة** (استقلالية اللقطة).

### الاشتراكات وخطط SaaS (المرحلة 8)

نظام اشتراكات متعدد المؤسسات بخط **FREE · BASIC · BUSINESS · PRO** — **بدون بوابة دفع في هذه المرحلة** (البنية جاهزة لربط Stripe أو غيره لاحقًا):

- **جدول `Subscription`** — سجل فريد لكل مؤسسة: `plan` + `status` (`trial | active | expired | cancelled`) + `trialUsedAt` / `trialEndsAt` + `currentPeriodEnd` (**محجوزة** لدورة الدفع المدفوعة المستقبلية) — هجرة `20260927000100_subscriptions`.
- **تجربة مجانية14 يومًا** تبدأ تلقائيًا مع كل مؤسسة جديدة (setup وregister) على خطة BUSINESS؛ عند انتهائها تُرقّى الحالة تلقائيًا إلى `expired` وتصبح الخطة الفعلية `free` (تطبيق كسول عند القراءة).
- **حدود لكل خطة** (جدول `PLAN_LIMITS` في `src/lib/plans.ts` — `null` = غير محدود):

  | الخطة | مستخدمون | منتجون | عملاء | فواتير | تخزين |
  |-------|---------|--------|-------|--------|-------|
  | FREE | 3 | 25 | 25 | 10 | 5 MB |
  | BASIC | 5 | 500 | 500 | 200 | 50 MB |
  | BUSINESS | 15 | 5000 | 5000 | 5000 | 500 MB |
  | PRO | ∞ | ∞ | ∞ | ∞ | 2048 MB |

  الحدود **مفروضة على الخادم** عند الإنشاء (مستخدمين/منتجات/عملاء/فواتير → `403` عند البلوغ) في `src/lib/server/resources.ts`، وبنفس القواعد في الوضع المحلي.
- **الاستخدام حقيقي دائمًا**: `COUNT` لكل مورد داخل المؤسسة + مساحة تخزين فعلية بـ `SUM(pg_column_size(*))` فوق كل جداول المؤسسة (لا أرقام ثابتة).
- **`/pricing` صفحة عامة** خارج المصادقة: بطاقات الأربع الخطط، مبدّل شهري/سنوي بأسعار DZD، شارة «الأكثر شيوعًا» على BUSINESS، وزر تبديل خطة فوري عند تسجيل الدخول.
- **`/subscription` + لوحة التحكم**: الخطة الحالية، حالة الاشتراك، عدّاد فترة التجربة، أشرطة الاستخدام والمتبقي لكل حد.
- **جاهزية الدفع**: تبديل خطة مدفوعة بعد انتهاء التجربة يُرفض `403` — نقطة ربط Stripe المستقبلية موسومة `[نقطة Stripe]` في `src/lib/server/subscription.ts` (تُستبدل بـ Checkout Session ثم Webhook يملأ `currentPeriodEnd`)، وأسعار `PLAN_PRICES` تجريبية للعرض فقط.
- قواعد التبديل **نقية ومشتركة** في `planSwitch()` بـ `src/lib/plans.ts` — مصدر واحد للحقيقة بين الخادم والموزع المحلي.

## 🗄 قاعدة البيانات (Multi-tenant)

### الجداول والعلاقات

```
Organization (المؤسسة — وحدة العزل)
├── User                (المستخدمون + الدور + passwordHash)
├── Customer            (العملاء)          ← Sale, Invoice
├── Supplier            (الموردون)         ← Purchase
├── Category            (الفئات)           ← Product
├── Product             (المنتجات)         ← Inventory, InventoryMovement, SaleItem, PurchaseItem
├── Inventory           (مستوى المخزون الحالي لكل منتج — سجل واحد فريد)
├── InventoryMovement   (سجل حركات المخزون — يغذّي صفحة المخزون)
├── Sale ── SaleItem ── Product
├── Purchase ── PurchaseItem ── Product
├── Invoice             (فواتير التحصيل)   ← Payment
├── Expense             (المصاريف)
├── Payment             (المدفوعات)
└── Notification        (الإشعارات)
```

كل جدول بيانات يحمل:

- `organizationId` — مفتاح خارجي إلى `Organization` **+ فهرس**، وكل استعلام يُفلتر به
- `createdAt` / `updatedAt` — تلقائيان من Prisma
- قيود تفرّد وعلاقات مرجعية (RESTRICT/CASCADE/SET NULL) حسب منطق العمل

### عزل المؤسسات — كيف يعمل؟

1. تسجيل الدخول يُصدر **كوكي جلسة** موقّعًا يحمل `userId` + `organizationId`.
2. كل مسار API يستدعي `requireOrgContext()` — يبني السياق من **الجلسة فقط** (لا من جسم الطلب).
3. `organizationId` **لا يُقبل أبدًا** من العميل — يُشتق من الجلسة عند الكتابة.
4. القراءة/التحديث/الحذف تستخدم `WHERE id = ? AND organizationId = ?` — سجل مؤسسة أخرى يعيد **404** (لا يكشف وجوده).
5. العلاقات المُرسلة (عميل/مورد/منتج في مستند) **تُتحقق** ضمن نفس المؤسسة قبل الإنشاء.
6. الصلاحيات تُفرض **على الخادم** أيضًا (نفس مصفوفة الواجهة) — تزوير الطرف الأمامي لا يفيد.

> مثال: مؤسسة A تحاول قراءة/تعديل/حذف عميل مؤسسة B → `404`، وبيع بمنتج مؤسسة B → `400`.

### التحقق والأخطاء

- **Zod schemas** لكل مورد (`src/lib/server/validation.ts`) — رسائل عربية + تفاصيل حقول في رد `400`.
- أكواد أخطاء ثابتة: `VALIDATION_ERROR / UNAUTHORIZED / FORBIDDEN / NOT_FOUND / CONFLICT / RATE_LIMITED / INTERNAL_ERROR`.
- أخطاء Prisma تُترجم (تكرار فريد → `409`، مرجع مفقود → `409`، سجل مفقود → `404`).
- الردود: `{ data }` عند النجاح، `{ error: { code, message, details? } }` عند الفشل — **لا تفاصيل داخلية أو هاشات كلمات مرور تُرسل للعميل أبدًا**.

### الـ API

```
POST   /api/auth/setup            إنشاء أول مؤسسة (مرة واحدة لكل نشر)
POST   /api/auth/register         تسجيل حساب جديد → مؤسسة + مالك + جلسة
POST   /api/auth/login            تسجيل الدخول → كوكي جلسة (حد محاولات 10/دقيقة)
POST   /api/auth/logout           تسجيل الخروج
GET    /api/auth/me               الجلسة الحالية
POST   /api/auth/forgot-password  طلب رمز استعادة (رد موحّد، صالح 30 دقيقة)
POST   /api/auth/reset-password   تعيين كلمة مرور جديدة → إبطال كل الجلسات
GET/PUT /api/settings             إعدادات المنشأة (من مؤسسة الجلسة فقط)
GET/PUT /api/subscription         اشتراك الخطة (الخطة/الحالة/التجربة/الحدود/الاستخدام) — PUT يتطلب settings.manage

POST   /api/v1/{resource}                 إنشاء
GET    /api/v1/{resource}/{id}            قراءة
PATCH  /api/v1/{resource}/{id}            تحديث جزئي
DELETE /api/v1/{resource}/{id}            حذف

# الموارد: customers, suppliers, categories, products, movements,
#          sales, purchases, invoices, expenses, users, payments, notifications
```

## 🔐 المصادقة والأدوار

### المصادقة

- **تسجيل حساب جديد** (`/register`): يُنشئ مؤسسة جديدة + مستخدم `OWNER` ويسجّل الدخول (البريد فريد عالميًا → `409` عند التكرار).
- **تسجيل الدخول** (`/login`): رسائل موحدة لا تكشف وجود الحساب + حد محاولات (`429` بعد 10 محاولات/دقيقة لنفس البريد).
- **تسجيل الخروج**: حذف كوكي الجلسة.
- **استعادة كلمة المرور**: `/forgot-password` يُصدر رمزًا عشوائيًا (يُخزَّن `SHA-256` فقط، صالح 30 دقيقة، استخدام واحد) → `/reset-password?token=…`. الرد موحّد دائمًا (لا كشف الحسابات). الإرسال عبر `EMAIL_WEBHOOK_URL` إن وُجد، وإلا يظهر الرابط تجريبيًا في وضع التطوير فقط.
- **إدارة الجلسات**: كوكي `HttpOnly` موقّع `HMAC-SHA256` لمدة 7 أيام، يحمل `sessionVersion` — أي تغيير لكلمة المرور يرفع الإصدار و**يُبطل كل الجلسات القديمة فورًا**.
- **حماية الصفحات**: في وضع `api` تُرفض الصفحات الخاصة بدون جلسة صالحة (تحويل إلى `/login`)، والجلسات المعطّلة/المحذوفة تُرفض عند كل طلب.
- كلمات المرور `scrypt + salt` — لا تظهر أبدًا في ردود API أو السجلات.

### الأدوار (الترتيب: OWNER › ADMIN › MANAGER › EMPLOYEE)

| الدور | الصلاحيات |
|-------|-----------|
| `OWNER` مالك النظام | صلاحية كاملة + وحده يعدّل مصفوفة الصلاحيات وينشئ/يحذف المالكين |
| `ADMIN` مدير النظام | إدارة معظم النظام (كل الوحدات) — لا يمسّ حسابات المالك |
| `MANAGER` مدير | المبيعات، العملاء، المخزون، المنتجات، المشتريات، الموردون، الفواتير، المصاريف، التقارير |
| `EMPLOYEE` موظف | إضافة المبيعات وعرض ما يُمنح له من صلاحيات (تُمنح/تُسحب من مصفوفة الصلاحيات) |

مصفوفة العرض/الإدارة لكل وحدة تُعدَّل من **المستخدمون والصلاحيات** وتُطبَّق فورًا على الواجهة **وعلى الخادم معًا**.

- حسابات تُنشأ من واجهة المستخدمين **بلا كلمة مرور** (لا تستطيع الدخول حتى تُعاد عبر الاستعادة).
- حسابات المالك محمية: لا يُعدّل دورها أو حالتها أو يُحذفها إلا مالك آخر، ولا يمنح دور المالك إلا مالك.

## 🌐 النشر على Vercel

### الطريقة 1 — من GitHub (مُوصى بها)

1. ارفع المستودع إلى GitHub ثم من [vercel.com](https://vercel.com): **Add New... → Project** — يكتشف Next.js تلقائيًا.
2. أضف متغيرات البيئة من **Settings → Environment Variables**:

   | المتغير | القيمة |
   |---------|--------|
   | `DATABASE_URL` | رابط PostgreSQL (Neon / Supabase / Vercel Postgres) |
   | `AUTH_SECRET` | `openssl rand -base64 32` (قيمة عشوائية جديدة) |
   | `NEXT_PUBLIC_DATA_PROVIDER` | `api` |
   | `EMAIL_WEBHOOK_URL` | (اختياري) بوابة إرسال البريد لروابط استعادة كلمة المرور |

3. اضغط **Deploy** — خطوة التركيب تُولّد Prisma client تلقائيًا (`postinstall`)، ويمكن تشغيل الهجرات من جهازك:
   ```bash
   DATABASE_URL="رابط-الإنتاج" npm run db:deploy
   ```
4. افتح الموقع وأنشئ مؤسستك من `/setup` أول مرة — أو سجّل حسابًا جديدًا من `/register`.

### الطريقة 2 — سطر الأوامر

```bash
npm i -g vercel
vercel          # بيئة المعاينة
vercel --prod   # بيئة الإنتاج
```

> في وضع `local` (بدون `NEXT_PUBLIC_DATA_PROVIDER`) لا حاجة لأي متغيرات — يُنشر كموقع يعمل فورًا.

### فصل الواجهة عن البيانات

الواجهة لا تعرف شيئًا عن التخزين — كل الوصول عبر `DataProvider`:

- `local-provider.ts` → localStorage (وضع MVP بلا خادم)
- `api-provider.ts` → `/api/v1/*` → **PostgreSQL**

التبديل بينهما بمتغيّر بيئة واحد `NEXT_PUBLIC_DATA_PROVIDER` — دون تغيير أي صفحة.
